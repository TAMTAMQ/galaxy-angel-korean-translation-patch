# 검수 중 반드시 지킬 제약

## C0. (최우선) 리터럴 `\n` 이 화면에 그대로 나온다 — 24건

`GADAT001_DAT_00125000` 의 `dialogue:0001` ~ `dialogue:0024` **연속 24건**에 줄바꿈이 아니라
**역슬래시 + n 두 글자**가 그대로 들어 있다. 한 번의 잘못된 번역 패스로 보인다.
이 파일의 나머지 158건과 다른 209개 파일에는 없다.

```
dialogue:0001  번역: 아버님, 이것은 대체 어찌 된 일인가요!\\n
               원문: お父様、これはどういうことですの！？
dialogue:0010  번역: 그런 제가, 에르시올을 떠날 수는 없습니\\n다!\\n
               원문: その私が、エルシオールから離れるわけには参りません！
```

**왜 검증을 통과하는가:** `\\n` 은 JSON에서 그냥 두 글자다. `validate` 의 `\r`·끝 `\n`·줄 수·열 수
검사 어디에도 걸리지 않는다. 그대로 빌드되면 화면에 `일인가요!\n` 이 보인다.

**추가 위험:** 이 엔진은 `\Speaker(...)` `\Face(...)` 처럼 **역슬래시를 명령 접두사로 쓴다.**
대사 본문 중간의 `\` 가 렌더러/토크나이저에서 어떻게 처리되는지 확인되지 않았다.

**대응:** 24건 전부 다시 번역하거나, `\\n` 을 실제 줄바꿈으로 바꾸고 44열·3줄로 다시 나눈다.
`dialogue:0001` 은 원문 `！？` 의 물음표까지 빠져 있으므로 문장부호도 같이 봐야 한다.
전수 검사 방법:

```bash
grep -n '\\\\n' work/galaxy_angel/assets/translation/segments/*.json
```

## C1. 문장을 늘리지 마라 — 파일마다 바이트 상한이 있다

`apply` 는 번역 후 시나리오 파일 크기가 원본을 넘으면 즉시 중단한다
(`translated scenario size changed`). 한글 1자 = 2바이트, 반각 1자 = 1바이트.

- 210개 중 **75개 파일이 여유 200바이트 미만**, 최소 **14바이트(한글 7자)**.
- 가장 빡빡한 파일: `GADAT001_DAT_0004b000`(14), `0002e000`(14), `000a0000`(14),
  `000a1000`(14), `000b8800`(15), `000d4800`(17), `000fc000`(18), `00107000`(19),
  `00100000`(20), `0003e000`(20), `0012d800`(20)
- 전체 목록은 **부록 1**.

**규칙:** 이 파일들에서 한 문장을 늘리려면 같은 파일 안에서 그만큼 줄여야 한다.
파일별 여유를 모른 채 "자연스럽게 풀어쓰기"를 하면 안 된다.

## C2. 선택지는 한 글자도 늘릴 수 없다 (124건)

선택지는 고정 바이트 슬롯이다. 원문 바이트 수를 넘으면
`translated selection exceeds original byte slot` 으로 중단된다.

- **여유 0바이트: 124건** (`★１０章★`→`★１０장★`, `↑戻る`→`↑복귀` 등)
- 여유 1~2바이트: 162건
- 목록은 **부록 3**.

## C3. 일반 대화는 한 줄 43열 이하, 최대 3줄

- 표시열: 반각 1열, 한글·전각 2열. 한글만이면 한 줄 약 21자 + 반각 1칸 정도가 안전하다.
- **실기 기준으로 44열은 안전하지 않다.** 44열째의 마지막 글리프가 문장부호 종류와
  무관하게 다음 표시줄로 밀릴 수 있다.
- 실제 재현:
  - `GADAT001_DAT_00006000:dialogue:0057`, `:0127`: 44열 끝 `,`가 다음 줄로 내려감.
  - `GADAT001_DAT_00009800:dialogue:0008`: 44열 끝 `!`가 다음 줄로 내려감.
  - `GADAT001_DAT_00009800:dialogue:0012`: 44열 끝 `.`가 다음 줄로 내려감.
- 따라서 원인은 쉼표 특수처리가 아니라 **일반 대화 렌더러의 44열 경계 자체**로 본다.
  게임용 폭은 한글/전각 2, ASCII 1로 계산하며, 문제 예시 두 건은 모두 정확히 44열이었다.
- `galaxy_angel_translation.py`는 일반 대화(channel != 0)를 **43열 안전 상한**으로
  재래핑한다. 기존 줄바꿈을 우선 보존하되, 뒤로만 밀면 4줄이 되는 경우에는 전체 문장을
  최대 3줄 안에서 다시 균형 배치한다. 공백 경계를 최우선으로 하고, 필요할 때만 문장부호
  뒤 또는 글자 경계에서 나눈다.
- 2026-09-10 전수 감사 기준: 정확히 44열인 줄 894개가 남아 있지만 빌드 시 43열 이하로
  자동 재배치되며, 새 규칙 적용 후 **최대 3줄 / 4줄 초과 0건**이다.
- 총량 자체가 3×43열에 들어가지 않거나 경계상 3줄 배치가 불가능했던 6개 대사는 별도
  축약/교정했다.
- channel 0 나레이션은 일반 대화창과 다른 경로이므로 기존 44열 검증을 유지한다.

**규칙:** 일반 대화(channel != 0)는 44열을 절대 목표치로 쓰지 말고 **43열 이하**로 잡는다.
문장부호가 `,`, `.`, `!`, `?` 중 무엇이든 44번째 열에 놓지 않는다. 3줄 대화는 특히
자동 줄바꿈으로 보이지 않는 4번째 줄이 생기지 않도록 전체 3×43열 안에 배치한다.

## C4. 새 한글 음절을 늘리지 마라 — 글리프 셀 여유가 132자뿐

폰트 하이재킹 방식이라 번역에 쓰인 고유 한글 음절마다 폰트 셀 하나가 필요하다.

- **실제 용량 1,352자**, 현재 사용 **1,220자**, 여유 **132자**.
- `assets/translation/README.md` 의 "안전 한도 고유 한글 2,045자" 는 **틀린 값**이다.
  2,045는 `is_script_safe_sjis` 필터 적용 전 셀 개수이고, 트레일 바이트가 ASCII(0x40~0x7E)인
  셀은 스크립트 파서와 충돌해 쓸 수 없다. 실제로 남는 셀이 1,352개다.
- 초과하면 `custom glyph capacity exceeded` 로 폰트 빌드가 중단된다.

**규칙:** 여유는 `galaxy_angel_font.py build` 를 실제로 돌려서 확인한다. README 숫자를 믿지 마라.

## C5. 원문에 없는 문자를 새로 만들지 마라 — 셀을 먹고 화면에 엉뚱하게 그려진다

현재 한글이 아닌데 전용 셀을 차지한 문자 6종:

| 문자 | 코드 | 건수 | 판정 |
|---|---|---:|---|
| `؟` 아랍어 물음표 | U+061F | 1건 | **오타. 고쳐야 한다** |
| `—` 엠대시 | U+2014 | 시나리오 58 + 전투 137 | 원문 `ー`/`～` 대체. 셀 낭비 |
| `·` 중간점 | U+00B7 | 시나리오 9 + 전투 255 | 원문은 `・`(U+30FB, cp932에 있어 셀 불필요). 셀 낭비 |
| `✕` | U+2715 | — | 셀 점유 |
| `ㄴ` 호환자모 | U+3134 | 1건 | `아・ㄴ・니` |
| `ㄹ` 호환자모 | U+3139 | 1건 | `ㄹ지도 모르겠지만` |

`·` → `・`, `—` → `ー` 로 되돌리면 셀 2칸이 즉시 회수된다.

**해당 위치:**
- `؟` : `GADAT001_DAT_0010c000:dialogue:0021` — `엣……!؟` → `！？` 여야 한다
- `ㄴ` : `GADAT001_DAT_00109800:dialogue:0109` — `아・ㄴ・니!`
- `ㄹ` : `remaining-compressed:00145` — 원문 `るかもしれませんけど。` 의 뒤 조각을 `ㄹ지도 모르겠지만 말이야.` 로 옮긴 것.
  앞 조각과 이어 읽어 판단해야 한다 (같은 내용이 `by_container/GADAT002.DAT.json` 에도 동기화되어 있다)

## C6. 전각 `～` 는 확정 규칙이다 — 되돌리지 마라

화면에 표시되는 물결표는 **반각 `~` 를 쓰지 않고 전각 `～`(U+FF5E)만 쓴다.**
반각 `~` 는 글리프가 나오기는 하지만 **위치와 크기가 너무 작게 그려지고 다음 글자와
너무 붙어 보여서** 전각으로 되돌린 것이다. 작업자가 **게임에서 직접 보고** 판단해
2026-08-26 에 결정했고 `STATUS.md` "표시용 물결표 전각 통일" 항목에 기록되어 있다.
GADAT001 대사·GADAT002 전투 대사·선택지·미니게임 ELF 문자열에 공통 적용되며,
`normalize_display_punctuation` 이 빌드 때 `~` → `～` 로 자동 교정한다.

**절대 하지 말 것:** 전각 `～` 670건을 반각 `~` 로 "정리"하는 것.
문서에서 범위를 뜻하는 `A~B` 는 화면 문자열이 아니므로 예외다.

**이 판정은 `~` 에만 적용된다.** 실기에서 확인된 것은 `~` 한 문자다.
`?` `!` `(` `)` 숫자 같은 다른 반각 문자는 **문제가 보고된 적이 없다.**
"같은 반각 테이블이니 나머지도 마찬가지일 것"이라고 추론해서 전각으로 되돌리지 마라.
새로 전각으로 바꾸는 판단은 실기에서 그 문자를 직접 확인한 뒤에만 한다.

**확정 규칙을 어긴 것 2건 (고쳐야 한다):**

| id | 원문 | 현재 번역 | 문제 |
|---|---|---|---|
| `GADAT001_DAT_00101800:dialogue:0057` | `で～す！` | `케이크 예-요!` | 전각 `～` 를 ASCII `-` 로 바꿨다. 이 규칙 위반 |
| `GADAT001_DAT_0000e800:dialogue:0012` | `大っきらいだぁ～っ！` | `싫어—!` | 전각 `～` 를 `—` 로 바꿨다. `validate` 의 `[가-힣]～+っ` 검사(물결 뒤 작은 `っ` 는 한국어 종성으로)도 이 치환 때문에 우회된다 |

**참고 — 시스템 영향이 있는 것은 `—` 뿐이다.**
엠대시 `—`(U+2014) 58건은 cp932에 없어 **전용 글리프 셀 1칸을 먹는다**(C4의 여유 132자에서 차감).
58건 중 57건은 원문이 `ー` 이므로 `ー` 로 되돌리면 셀 1칸이 회수된다.
ASCII `-` 74건 중 72건도 원문이 `ー` 지만 이쪽은 셀을 먹지 않으므로 시스템 영향은 없다.
둘 다 원문 문자를 바꾼 것이라 원본 보존 관점의 사안이며, **번역 검수 쪽 판단 영역이다.**

## C7. 전투 대사 창 폭 — 실기에서 40열부터 잘림 확인

- 원본 일본어 전투 대사는 한 줄 **최대 34열**을 한 번도 넘지 않는다.
- 2026-09-10 실기 확인으로 전투 메시지 창은 **최대 3줄**이며, 한국어 장문이
  40~42열 부근에서 오른쪽을 벗어나 잘리는 것이 확인됐다.
- 실측 사례:
  - `remaining-compressed:00489` 기존 44열. 실제 화면은 41열 상당인
    `지휘를 잘못해서 지고 싶지는 않으니까 말이`까지만 보였다.
  - `remaining-compressed:00523` 기존 47열. 42열 상당인
    `그럼, 주요 명령을 내리는 방법을 구체적으로`까지만 보였다.
  - `remaining-compressed:00567` 기존 45열. 40열 상당인
    `그럴 경우에는, 우리들의 판단으로 싸울 테`까지만 보였다.
- 따라서 **39열을 전투 창의 하드 상한**으로 두고, 튜토리얼처럼 긴 설명문은 가능하면
  37열 이하로 더 여유 있게 맞춘다. 픽셀 폭은 글리프에 따라 차이가 날 수 있으므로
  39열은 '채워야 하는 목표'가 아니라 현재 실기에서 확인된 최단 잘림점 40열 바로 안쪽의 방어선이다.
- 이번 수정에서 `TUT_*`의 38열 이상 28개 레코드를 전부 정리해 **최대 37열**로 만들었다.
  한 문장이 다음 물리 레코드로 확실히 이어지는 경우에만 내용을 다음 레코드로 재분배했고,
  독립 문장은 자체 축약했다.
- `battle_unique.json`의 기존 40열 이상 고유 대사 17개도 축약/재배치해 **40열 이상 0건,
  최대 39열**로 만들었다. 권위본이므로 빌드 시 해당 반복 occurrence 전체에 전파된다.
- `galaxy_angel_build_battle.py`는 이제 전투 고유 대사와 `TUT_*`에 대해 **3줄 초과 또는
  한 줄 39열 초과를 빌드 오류로 차단**한다.

부록 4의 127개 목록은 이번 수정 **이전**에 발견했던 40열 이상 반복 occurrence의 진단 기록이다.

# 남은 구조적 위험

## R1. 폰트 문자 수집 경로에 빈틈이 있다

폰트 빌더 `collect_custom_chars` 가 읽는 파일과 실제 빌드가 쓰는 파일이 다르다.

| | 폰트 빌더가 읽음 | 빌드가 실제로 씀 |
|---|---|---|
| 시나리오 | `segments/*.json` | 같음 |
| 선택지 | `selection_translations.json` | 같음 |
| 화자명 | `speaker_names.json` | 같음 |
| 전투 | `battle/battle_unique.json` | **`battle/segments/*.json`** |
| remaining | `remaining/remaining_compressed_unique.json` | 같음 + **`remaining/by_container/GADAT002.DAT.json`** |

현재는 문자 집합이 우연히 일치해 문제가 없다(`battle/segments` 728종·`by_container` 524종 모두 폰트맵에 포함).
그러나 **`battle/segments/*.json` 이나 `by_container/*.json` 만 직접 고쳐 새 음절을 넣으면**
폰트 빌더가 그 문자를 모른 채 넘어가고, `encode_text` 가 cp932 인코딩을 시도하다
`UnicodeEncodeError` 로 죽는다.

**대응:** 전투·remaining 검수는 `battle_unique.json` / `remaining_compressed_unique.json` 쪽에서 하고
`galaxy_angel_sync_extracted_translations.py` 로 occurrence 파일에 동기화한다.
`battle/battle_units.json`(37,805개)은 빌드가 읽지 않는 사본이다.

## R2. `remaining_direct_review.json` 1,070개는 게임에 반영되지 않는다

전부 `use_translation: false` 다. 번역문은 채워져 있으나 개발 로그·문자표·오검출 바이트열이
섞여 있어 의도적으로 끈 상태이며 `remaining/README.md` 에 명시되어 있다.
결과적으로 실행 파일 문자열 1,069개 + MINI.DAT 1개는 **게임에서 일본어로 나온다.**
릴리스 노트의 알려진 제약에 넣어야 한다.
